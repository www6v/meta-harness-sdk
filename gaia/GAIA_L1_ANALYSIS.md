## 五、关键发现

1. **Web 能力是胜负手**:59% 的题依赖 `web_search` + `web_fetch`,Tavily + 海外 Markdown 服务部署后能解锁大多数题。

2. **多跳查询是真正难点**:
   - Q6:论文 → 作者列表 → 该作者第一论文
   - Q42:TV 节目 → 餐厅 → 推荐书籍
   - Q46:新闻文章 → 链接论文 → NASA 资助编号
   
   单次搜索不够,需要链式查找。

3. **文件题是得分富矿**:7 题只要能把文件内容拉进上下文(文本/表格/代码),LLM 就能推理。投入产出比最高。

4. **答案格式简单**:87% 是短文本或数字,不需要复杂格式化,只要找对答案。

5. **指令遵循题易翻车**:Q24 这种"不要答题只写 Guava"的题考验模型抗干扰能力,容易过度思考。

6. **数值精度敏感**:Q1、Q52 等需要精确计算(四舍五入、小数位),bash 计算优于 LLM 心算。

### 8.3 发现的系统缺陷与修复状态

#### ✅ **缺陷 1:Session 终止失败 (严重度:P0) - 已修复**

**现象**:旧版本 100% 的题目都超时,即使 agent 已经找到正确答案。

**根因分析**:
- Runner 手动处理 SSE 流时,无法正确解析嵌套的 `stop_reason.type` 结构
- SSE 连接在退出时阻塞,导致程序挂起

**修复方案**(2026-07-19):
- ✅ 使用 OMA SDK 的 `stream_until_end_turn()` 替代手动 SSE 处理
- ✅ SDK 自动处理事件流解析、重连、终止条件
- ✅ 正确的 `stop_reason.type` 提取逻辑

**修复效果**:
- 超时率:**100% → 12.5%** (仅 2 题超时)
- Q2 耗时:**超时 → 73s** (答案正确)
- 测试效率提升:**10 倍+**

#### 🔴 **缺陷 2:答案提取失败 (严重度:P0) - 待修复**

**现象**:81.3% 的题目 agent 找到了答案但没有输出 `ANSWER:` 格式,导致无法提取。

**根因分析**:
- Agent 的 system prompt 没有强制要求输出 `ANSWER:` 格式
- Agent 在推理过程中没有明确的"答案输出"步骤
- 部分题目 agent 推理正确但没有格式化输出

**证据**:
```
Q4 (5d0080cb):
  - 工具调用:2 次 (成功)
  - 耗时:41s
  - 状态:no_answer (从未输出 ANSWER 行)
  - 正确答案:`0.1777`
  - 问题:agent 找到了信息但没有格式化输出

Q9 (2d83110e):
  - 工具调用:0 次 (纯推理题)
  - 耗时:33s
  - 状态:no_answer
  - 正确答案:`Right`
  - 问题:agent 理解了反转指令但没有输出答案
```

**影响**:这是当前通过率低的**主要原因**。如果能修复,预计通过率可提升至 **60%+**。

**修复建议**:
1. 在 system prompt 中强制要求:
   ```
   You MUST end your response with a line exactly in this format:
   ANSWER: <your_final_answer>
   The <your_final_answer> is the shortest possible string that answers
   the question (number, name, date, short phrase).
   ```
2. 添加 few-shot 示例,展示如何输出 ANSWER
3. 在 agent 推理结束后,如果检测到没有 ANSWER,主动追问

#### 🟡 **缺陷 3:多跳查询能力不足 (严重度:P1) - 待优化**

**现象**:Q6(学术作者链)、Q42(节目→餐厅→书)等多跳查询失败。

**根因分析**:
- Agent 在第一次搜索后没有找到足够的线索进行下一步
- 缺乏"链式搜索"策略:找到 A → 从 A 提取信息搜索 B → 从 B 提取信息搜索 C
- Q6 做了 10 次工具调用但仍然没有提取出答案

**证据**:
```
Q6 (46719c30):
  - 工具调用:10 次 (web_search × 5, web_fetch × 5)
  - 状态:no_answer (从未输出 ANSWER 行)
  - 正确答案需要:论文 → 作者列表 → 筛选有前置论文的作者 → 该作者第一论文标题
```

**影响**:约 20% 的 Web 检索题需要多跳查询,这是拉开差距的关键能力。

**修复建议**:
1. 在 system prompt 中强调"链式搜索"策略
2. 教 agent 在每次搜索后提取关键实体,用于下一步搜索
3. 考虑添加专门的"multi-hop search"工具

#### 🟡 **缺陷 3:答案提取不完整 (严重度:P1)**

**现象**:Q20 找到 "Annie" 但漏掉 "Levin";Q43 找到 "9" 但正确答案是 "519"。

**根因分析**:
- Agent 在 web_fetch 返回的长文本中迷失,没有精确定位答案
- 缺乏"答案验证"意识:找到候选答案后应该回查问题确认完整性
- Q43 可能只看到了部分统计数据

**证据**:
```
Q20 (5188369a):
  - 预测:Annie
  - 正确:Annie Levin
  - 工具调用:2 次 (web_search, web_fetch)
  - 分析:agent 找到了名字但漏掉了姓氏

Q43 (3f57289b):
  - 预测:9
  - 正确:519
  - 工具调用:5 次
  - 分析:agent 可能看到了错误的统计列(保送 vs 打数)
```

**影响**:即使找到相关信息,答案不完整也算错。

**修复建议**:
1. 在 system prompt 中强调"完整答案":人名要全名,数字要准确
2. 添加答案验证步骤:输出 ANSWER 前回查问题
3. 对于数值答案,要求 agent 说明数据来源(哪一列、哪一年)
